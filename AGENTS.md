# AGENTS.md

Hackathon project (Junction x Turku 2026): **AMRight**, a continuously updated antimicrobial resistance (AMR) monitoring tool. A doctor describes a patient and sees which antibiotics are likely to cover it (with honest ranges), the likely organisms, the last 4 weeks beside the last 12 months, and anomaly alerts. Everything is also exposed as an API, an MCP server and a chat agent.

## Data

Fully synthetic microbiology dataset in [data/synthetic_microbiology_dataset/](data/synthetic_microbiology_dataset/). Read its [README.md](data/synthetic_microbiology_dataset/README.md) before working with the data. ML pipeline notes: [data/AEI_ML_PIPELINE.md](data/AEI_ML_PIPELINE.md).

Files (CSV, UTF-8): `patients.csv`, `cultures.csv` (urine, blood, wound), `isolates.csv`, `susceptibility.csv` (S/R only), `antibiotics.csv`, `wards.csv`. Structure: patients → cultures → isolates → susceptibility, joined on `patient_id`, `culture_id`, `isolate_id`.

Rules that every number must follow:

- Resistance and coverage use the **first isolate per patient**, deduplicated within each rolling window.
- Require at least 30 isolates; below that, shrink toward the hospital rate (beta-binomial, `backend/app/shrinkage.py`) and report the sample size and how much the estimate leans on the prior.
- Every query takes an `as_of` date (default 2026-09-27, the end of the data; range 2023-10-02 to 2026-09-27). Nothing after `as_of` may influence a result; `test_datalayer.py` asserts that.
- No diagnoses and no respiratory samples in the data: specimen stands in for infection type. Call the output "local susceptibility coverage", never a prescribing recommendation, and give no dosing.
- Carry S, I and R everywhere even though the data has only S and R. Aggregates only, no patient identifiers, except the optional patient-context endpoint.

## Layout

- `backend/app/` — FastAPI app (Python 3.12, pandas, scipy, pydantic v2).
  - `registry.py` — **declare each function once** with `@register(name, description, path, input_model, output_model)`; REST routes are generated from it, GET results are remembered per (function, input) in memory (the data never changes; `cache=False` for the dashboard), and the MCP server and the Claude agent tools will read the same registry (one set of functions, three callers). `GET /v1/functions` and `GET /v1/widgets` expose the registry and widget catalog as data.
  - `functions/` — handlers (`data.py`, `alerts.py`, `dashboard.py`). `models/` — request/response pydantic models. `vocab.py` — shared literals (wards, specimens, organisms, WHONET drug codes, age bands, windows, `MIN_ISOLATES`). `widgets/catalog.py` — widget names → parameter schemas; the AI picks widgets and params, it never writes a number.
  - `datalayer/` — `store.py` (load the six tables from Postgres in Azure (`DATA_SOURCE=postgres`) or from the CSVs locally, isolate frame, first-isolate rule, `as_of` cut, window dates, `sir_rows`: S/I/R rows by integer-coded filters, small results remembered), `derive.py` (age band, onset, week start), `susceptibility.py` (shrunk estimates, outbreak-inflation flag, weekly series), `coverage.py` (organism mix, WISCA coverage per drug and pair, narrowest effective drug). `volume.py` (weekly culture counts per ward and specimen, seasonal baseline, `get_volume`), `alerts.py` (alert detectors in `DETECTORS`, alert list and detail; add new detectors there), `signals.py` (ward x organism cells clearly above the hospital rate, per day, cached; built on `susceptibility.py`), `trend.py` (monthly Mann-Kendall + Sen slope for slow drift). `spreading.py` (flag counts per ward against the ward's own year, `spreading_series`: the same flags per 7-day block for the last 12 weeks with the typical weekly count and the organisms per ward, ward links by shared patients within 30 days, cross-ward warnings from active alerts on linked wards). `shrinkage.py` — the shrinkage maths.
  - `agent/` — the chat agent (`POST /v1/agent/screen`, server-sent events) and the "In short" line of three results pages (`GET /v1/agent/in-short`, `/in-short/alert`, `/in-short/spreading`). `schema.py` (request, with the held `profile` and up to 24 earlier turns in `history` so a short reply is read as the answer to the last question, and the wire format: chrome events `header`/`status`/`error`/`done` mirror the Flutter `AgentEvent` types, the answer itself is `a2ui` events), `a2ui.py` (turns the loop's widget/in_short/clarify events into one A2UI v0.9 surface per answer: `createSurface`, then one `updateComponents` per part with the root `Answer` listing the children; catalog id shared with the app), `summary.py` ("In short": one `Kind` per page (COVERAGE: coverage, organism mix and active alerts for the `/v1/coverage` query; ALERT: the alert detail and the ward's links; SPREADING: spreading, the page's own 4-week counts for the ward it leads with, and that ward's links); Claude writes one line through the `in_short` tool with drug and ward names, numbers checked by `numbers.py` and rewritten once, remembered per page and query), `prompt.py` (frozen system prompt; the widget catalog in it is generated from `widgets/catalog.py`), `tools.py` (registry functions as read-only data tools, plus `render_widget`, `in_short`, `ask_user`; every input is validated), `llm.py` (`ClaudeClient` over `AsyncAnthropic`; the offline tests play a scripted `FakeClient` from `backend/tests/fake_llm.py`), `loop.py` (manual tool loop, 8 iterations at most, widgets sent as soon as their input is complete, summary checked by `numbers.py`; a summary in the same turn as a refused widget is held back until the widget is fixed), `route.py` (SSE with a `: ping` every 15 s, A2UI via `a2ui.to_a2ui`; the in-short routes take their page's query; all 503 without a key).
  - `mcp_server.py` — the MCP server at `/mcp` (streamable HTTP, stateless JSON): every GET function in the registry except the dashboard as a read-only tool, same handlers and result cache as REST. `auth.py` — demo-grade API key (`API_KEY`): `/mcp` always needs `X-API-Key` (or `Authorization: Bearer`); `/v1/*` needs it unless the request's `Origin` is one of `CORS_ORIGINS` (no wildcard: in Azure only this app's Static Web App and `amright.mankeli.co`); `/healthz` and `/v1/data-status` are open; no key set means open (local, tests). `ratelimit.py` — per-IP limits (rightmost public `X-Forwarded-For` address, IPv6 per /64, in each worker's memory) on `POST /v1/agent/screen`, `/v1/agent/in-short*` and `PUT /v1/dashboard`, 429 with `Retry-After`; on only when `API_KEY` is set. `PUT /v1/dashboard` takes at most 50 pins and 20,000 characters of layout, `user_id` at most 64.
  - `fixtures/` — canned responses that keep the contract stable while real implementations land.
  - `db.py` — tiny psycopg connection and `ping()`. `schema.sql` — Postgres schema.
  - `warmup.py` — the queries the screens send at their defaults (home, hygiene, lab, doctor per ward and infection type, Research E. coli/TMP), run once at start into the result cache; with `PRELOAD_WARM=true` and `gunicorn --preload` it runs in the master before the workers fork, so the port opens only when everything is warm (budget `WARM_BUDGET_SECONDS`, default 120). Add a query here when a screen gets a new default; `test_warmup.py` checks the list against the registry.
  - `config.py` — settings from env / `backend/.env`; `DATA_SOURCE` is `postgres` in Azure (the deploy zip has no CSVs) and `csv` by default for local work and the unit tests; `WARM_UP` (default true) computes the alert signals in a background thread at startup (about 12 s on a laptop).
- `frontend/` — Flutter web app (flutter_bloc, go_router); structure and rules in [frontend/README.md](frontend/README.md). `lib/ds/` is the design system with the exact tokens from the design canvas (Sora + Inter bundled in `assets/google_fonts`). `lib/core/` holds the transport (HTTP or `assets/fixtures`), typed models mirroring `backend/app/models`, the cached `AmrRepository` and `QueryView`. `lib/session/` holds the demo users and the replay `as_of`. `lib/catalog/` holds the widgets placed by name + params: same names as `widgets/catalog.py`, and a GenUI `CatalogItem` wraps each entry. `lib/features/` holds the screens (login, doctor, hygiene, lab, research, chat, dashboard, components). `web/` holds the loading screen (`index.html` + `flutter_bootstrap.js`: gradient, name, a progress bar that eases through Flutter's start-up stages and fades on `flutter-first-frame`), the favicons and the PWA icons. `--dart-define=API_BASE=...` or `--dart-define=FIXTURES=true`.
- `infra/` — Bicep (Key Vault, Postgres, App Service, Static Web App, monitoring). `scripts/` — deploy, OIDC bootstrap, Anthropic key, DB helpers. `.github/workflows/` — backend, frontend, infra what-if.

## Status

The header profile is a static name/context and avatar display (avatar only on phones), with no user menu, hover action or keyboard focus. Desktop replay and Switch user remain separate controls.

Real (computed from the data): data layer (#5), `GET /v1/susceptibility` and `/v1/susceptibility/series` with shrinkage (#6), Azure infrastructure and CI (#3), Postgres schema, CSV loader, DB-backed `/healthz` and `/v1/dashboard` (#11), `GET /v1/volume`, `/v1/alerts` and `/v1/alerts/detail` with sentinel (every CPE and VRE isolate) and missing-data alerts (#8). Statistical alerts (ESBL/MRSA flags and multi-drug rises above the hospital rate) and the hospital-wide trend alert (#9); `Alert.ward` is `None` for a trend. `GET /v1/spreading` and `/v1/ward-links` with cross-ward warnings (#10): a link is a patient sampled on both wards within 30 days (ED: PHC-N 413, GER 325, URO 291), a warning needs an active statistical or sentinel alert on the linked ward and a link of at least 5% of the smaller ward's patients. Rule scores: `docs/alert_evaluation.md`.

Infection control (`/hygiene`) is the visual design from the design canvas page "Infection control · visual": hero ward, ward tiles with sparklines, ward detail with weekly bars, linked-wards flow and heads-up. It reads `GET /v1/spreading/series` (new, real), `/v1/spreading` and `/v1/ward-links`; "Export" copies the weekly counts as CSV, "Pin to my home" pins `SpreadingCounts`, the heads-up is local only.

Chat agent (#12): `POST /v1/agent/screen` streams the answer Claude builds from the catalog as an A2UI v0.9 surface (`agent/a2ui.py`); tested offline with the fake client and live with `pytest -m live` (needs `ANTHROPIC_API_KEY`). The Flutter chat renders it with Google's `genui` (0.10.x, with `a2ui_core` and `json_schema_builder`): `RemoteAgent` (`features/chat/agent/remote_agent.dart`) reads the SSE stream over `package:http`'s fetch client, `ChatCubit` hands each A2UI message to a genui `SurfaceController`, and `ChatAnswer` shows the answer as a genui `Surface` built from `features/chat/answer_catalog.dart` (every `WidgetCatalog` entry as a `CatalogItem`, plus `Answer`, `InShort` and `Clarify`; a tapped clarify option is a `choose` user action). Asked to warn a named ward, the agent places `CrossWardWarning` with `to` (the wards to warn; never the ward the bacteria are on), and the chat shows one "Send heads-up to …" button that opens the usual draft: the user checks and sends, the agent never does (sending is still local only). Each question carries the last 12 turns (`ChatCubit._history`: the user's questions and, per answer, `AnswerEntry.describe()`: what it showed or asked). Follow-up actions and suggestions are built in the app from the widgets placed (`followUps`), not by the AI. There is no scripted stand-in: without a backend (fixture mode) or a key the chat offers the quick patient form, and the widget tests inject `test/support/canned_agent.dart` (`AmrApp(agent:)`), which sends the same A2UI through `AnswerSurface`. Answers are saved as their A2UI components and put back on surfaces when a chat is reopened. The chat scrolls a new question to the top and lets its answer build below it: the latest turn is the `CustomScrollView` center, so earlier answers that are still loading never push it down. "In short" (`AiInShort` in `catalog/widgets/in_short.dart`) sits on the doctor answer page, the lab's alert page (under the alert's paragraph) and infection control (under the hero, about the ward it leads with); each keeps a placeholder when AI answers are off.

No endpoint returns a canned response any more; `fixtures/data.py` only supplies the `window_out` helper (`fixtures/alerts.py` is unused).

Flutter app (#14–#18 UI side): every screen and component in the design canvas, desktop and phone. Demo login with roles, a top bar that stays pinned and frosts over once the page scrolls (`features/shell/sticky_top_bar.dart`), replay slider, typed API client and fixture mode, the doctor flow (patient form → answer page), infection control (`/hygiene`, care workers see their wards first), lab inbox and investigation (`/lab`, `/lab/alerts/:id`), research Explore with chart, table and CSV export (`/research`), chat (`/chat?q=`), pinned widgets on `/v1/dashboard`, and a live component gallery (`/components`). The 17 catalog widgets match `widgets/catalog.py`. Every "Ask" field is an `AskLauncher` (`features/chat/widgets/ask_launcher.dart`): tapping it lifts a larger composer to the top over a frosted page, Enter or a suggestion opens the chat, and Esc, a tap outside or Cancel puts it back with the draft kept. Each one takes an `AskContext` (`features/chat/ask_context.dart`: patient form, answer, spreading, alerts, research, dashboard) that sets the composer's title and suggestions; from an answer page the patient goes along (`/chat?q=…&ward=…`, `CatalogActions.ask(q, patient:)`), so follow-ups are answered for that patient. The chat asks the Claude agent (#12) through `RemoteAgent` behind the `ChatAgent` interface (see Chat agent above). Chat history: `ChatCubit` keeps the open conversation and up to 30 earlier ones per user in the browser (`shared_preferences`, a fresh agent per conversation); a side panel on wide screens, a "Chats" drawer elsewhere, and New chat. A question from any ask field outside the chat (`/chat?q=…`) starts a new conversation; asks inside the chat continue the open one. Patient history reads a fixture (no endpoint yet); "Mark as reviewed" and "Send heads-up" are local only (no backend endpoints).

MCP server (#13) is built (`/mcp`, tested in `test_mcp.py`; the deploy checks that it answers 401 without the key). In Azure the app reads the dataset from Postgres at startup (`DATA_SOURCE=postgres`, about 7 s) and computes in memory; locally it reads the CSVs unless `DATA_SOURCE=postgres`. Postgres is loaded by `scripts/load_data.py --dsn ...` (idempotent) and also holds app tables such as `user_dashboards`. `TEST_DATABASE_URL=... pytest` also runs the test that checks the Postgres tables equal the CSVs. `/healthz` returns 503 unless the database answers (`backend/app/db.py`).

When you replace a fixture with a real implementation, keep the input/output models unchanged (the frontend codes against them), drop the `fx.` call from the handler, and add tests.

Build order (from #1): data and `as_of` → coverage/organisms/filters → alerts (sentinel, statistical, trend, missing data; four planted signals in the data, measure weeks-to-detect and false alarms) → replay slider → API + MCP → chat agent and dashboard → lab extras. Protect the non-AI steps first.

## Commands

```bash
python -m venv .venv && source .venv/bin/activate && pip install -e ".[dev]"
ruff check backend && pytest                     # CI runs both
cp backend/.env.example backend/.env             # read from any working directory; leave ANTHROPIC_API_KEY empty: agent routes return 503, rest works
uvicorn app.main:app --reload --app-dir backend  # API on :8000, docs at /docs
ANTHROPIC_API_KEY=... .venv/bin/pytest -m live -s backend/tests/test_agent_live.py   # the real Claude API, a few cents
.venv/bin/python scripts/evaluate_alerts.py --quick   # weeks-to-detect and false alarms per ward-year for every alert rule (--out FILE writes markdown)
docker compose up -d db                          # optional local Postgres
cd frontend && flutter pub get && flutter analyze && flutter test
flutter run -d chrome --web-port 8080 --dart-define=API_BASE=http://localhost:8000 --web-browser-flag=--disable-backgrounding-occluded-windows  # CORS allows :8080; the flag keeps hot restart working while the window is behind others
flutter run -d chrome --dart-define=FIXTURES=true                                   # no backend needed (no AI: the chat offers the quick form)
```

## Conventions

- Python: ruff, line length 100. Pydantic models for every input and output; no `from __future__ import annotations` in `registry.py` (annotations are built dynamically).
- Models: the Claude API (`ANTHROPIC_MODEL`, set in env); the key lives in Key Vault in Azure and never reaches the client.
- Secrets and `.env` are gitignored; do not commit keys. Infra and deploy specifics are in [docs/azure.md](docs/azure.md).
- Commits and PRs reference the issue they close (e.g. `(#6)`).
- **Keep this file current.** Update AGENTS.md in the same change whenever something new is added or something changes that it documents: a fixture replaced by a real implementation (update Status), a new function, module, directory, command or env variable, a changed rule or convention, a finished or newly opened issue. Do not leave it for later; an outdated AGENTS.md is a bug.
